# 가나다계단 백엔드 개발 계획

개발 계획 PDF는 교사·학생이 수행할 흐름을 정하는 데 사용했습니다. ZIP의 API 명세, mock, 테스트 및 연결된 프론트엔드는 HTTP 계약의 기준으로 삼았으며, DML과 20개 테이블 DDL을 상태·권한·트랜잭션 설계에 반영했습니다. 교사 자료 열람 범위는 협의대로 클래스의 담당 교과로 제한합니다. PDF의 다른 교과 자료 표시 요구는 이 권한에 맞춰 적용 범위에서 제외합니다.

## 현재 구현과 MariaDB 매핑

`app/main.py`가 슬라이스를 조합합니다. 각 슬라이스 내부에서 입력·출력 모델을 정의하고, 라우터가 HTTP를 처리하며, 서비스가 그 기능의 상태 전이와 검증을 담당합니다. 세션·멤버십 권한, 오류 형식과 ETag, 테스트용 메모리 상태는 `app/core`에서 공유합니다. 화면 집계는 기존 슬라이스의 조회 결과를 사용합니다.

| 슬라이스 | 검증 가능한 흐름 | MariaDB 11.8 연결 시 사용할 DML과 테이블 |
| --- | --- | --- |
| `identity` | 역할 선택 로그인, 교사 승인 확인, 해시 세션·만료·CSRF·로그아웃. 학생의 소속과 진단 상태에 따라 `nextAction` 계산 | A00–A01, `users`, `user_sessions`. 계정 발급·비밀번호 재설정의 운영 흐름은 별도 확정 |
| `classes` | 내 클래스 목록, 교사 클래스 개설, 사용 횟수·만료·역할이 있는 초대 발급 및 수락. 교사 초대의 교과는 소유자가 지정 | B00–B03, `classes`, `class_memberships`, `class_invitations`. 개설과 소유자 소속 생성, 초대 잠금·가입·사용 횟수 갱신을 각각 한 트랜잭션으로 처리 |
| `diagnostic` | 계정당 최초 진단 한 번, 시작 시 버전 고정, 제출하지 않은 첫 문항으로 재개, 명시적 모름, 동일 답안 재전송, 마지막 제출 시 파트 10개·영역 5개 계산 | C00–C05, D00, J00, `diagnostic_forms`, `diagnostic_questions`, `student_diagnostics`, `diagnostic_answers`, `diagnostic_part_results`, `diagnostic_area_results`. 진단 행을 잠근 뒤 마지막 답안·결과·완료 상태를 동시에 확정 |
| `materials` | 업로드 및 PDF 텍스트 추출 → 원본 등록·권한 기반 다운로드 → 학생별 전환본 수정·검토·배포. 수정하면 검토가 풀리고 배포본은 고정 | E00–E02, G00–G01, I00, K00–K01/K03, `files`, `source_materials`, `student_materials`. 파일의 검사 상태와 저장소 키를 먼저 검증하고 원본을 잠가 새 revision을 할당 |
| `quizzes` | T/F·4지선다 초안 검증, 수정·검토·배포, 답안·오답 재풀이, 제출 후 해설, 최초 성적과 현재 오답 분리 | H00–H01, I00–I03, K00–K02, `quizzes`, `quiz_questions`, `quiz_submissions`, `quiz_answer_attempts`. 문항 수정과 부모 버전 갱신을 묶고, 풀이 시 제출 행을 잠가 멱등키 확인·답안 기록·첫 성적 확정을 처리 |
| `dashboard` | 교사 학생 수준표·담당 교과의 최근 풀이·검토 대기, 학생 배포 자료·문항 진행. 진단 영역 선택과 배정 콘텐츠 권한은 독립 | D00, I00/I04, K00의 기존 테이블을 조회해 계산. 학생별 문항 수와 문제 묶음 수, 최근 7일 배포 여부와 풀이 상태를 구분 |
| 후속 작업 | 생성 작업·교사별 AI 키 등록 및 확인 | F00–F02, G00/H00, `ai_credentials`, `ai_requests`. 작업 접수·조회 2개와 키 관리 4개 API는 생성 기능 통합 시 추가 |

DTO는 `/api/v1`, camelCase, 문자열 ID와 목록의 `items/nextCursor`를 유지합니다. `studentMemberId`는 클래스 소속 ID입니다. `sourceId`는 업로드한 원본, `materialId`는 학생에게 배정된 전환본, `quizId`는 학생에게 배정된 문제 묶음입니다. DB에서는 bigint 값을 문자열로 직렬화합니다. 현재 계약에는 한 페이지 전체를 반환합니다.

## 팀원 작업 연결 지점

| 팀 작업 | 넘겨줄 값과 접점 |
| --- | --- |
| 진단 문항·정답·제시 방식 | 팀 데이터에서 `DiagnosticForm`과 `DiagnosticItem`을 매핑하고 `create_app(diagnostic_form_provider=...)`에 `FormProvider`를 주입합니다. 제시용 `QuestionDisplay`와 채점용 정답·배점·판정 슬롯은 분리합니다. 서비스가 공식 문항 수를 결정하지 않으며, 가상 문항집의 70문항은 테스트 데이터입니다. 새 버전은 새 진단에 사용하고 기존 진단은 시작 때 선택된 버전을 계속 사용합니다. |
| 자료 제작 | 팀 기능의 전환 결과를 `app.materials.dto.Content`의 문단·번역 DTO로 변환해 `app.materials.service.create_draft(store, teacher, source_id, student_member_id, content)`로 연결합니다. 서비스가 학생의 진단 완료와 클래스·교과 권한을 확인하고 전환본 초안과 진단 스냅샷을 저장합니다. PDF 출력이나 변환 구현은 팀 모듈에서 제공합니다. |
| 문항 생성 | 팀 기능의 결과를 `app.quizzes.dto.QuizDraft`에 매핑하고 `app.quizzes.service.create_quiz_draft(store, teacher, draft)`로 연결합니다. 출처는 원본 또는 같은 원본·학생의 배포 전환본입니다. 문항 유형별 보기 수, 정답 ID, 해설 및 출처 문장 ID를 검증하고 교사 검토 전 상태의 초안을 저장합니다. |

이 연결 지점은 서버 내부에서 호출합니다. 생성 워커 연동 시 작업의 교사·클래스·원본·학생을 저장된 요청에서 가져오고 권한을 다시 확인합니다. 메모리 모드에서는 HTTP 요청을 직렬화하며, 워커를 추가할 때는 초안 생성과 작업 성공 기록을 저장 트랜잭션으로 묶습니다. `create_app(store=...)`를 쓰면 테스트나 팀 통합에서 별도 메모리 상태를 주입할 수 있습니다. 이 경우 자동 시드가 실행되지 않으며 진단 문항집도 명시적으로 주입할 수 있습니다.

## 후속 단계와 완료 기준

1. **MariaDB 연결 시 인증·클래스부터 전환**
   DDL 원본을 기준으로 버전 관리되는 마이그레이션과 연결 설정을 준비합니다. 저장소를 슬라이스별 조회와 유스케이스 단위 트랜잭션으로 교체합니다. 교사 초대의 교과를 자동으로 확정하려면 기존 초대 DDL에 담당 교과 컬럼을 추가하는 안을 검토합니다. 운영 계정 발급과 교사 승인 절차를 결정합니다. 완료 기준은 세션·소속의 재시작 후 유지, 만료 초대 거부, 동시 수락 시 사용 한도 준수입니다.
2. **공식 진단 문항집 결합 및 파일 저장 영속화**
   팀원이 넘긴 공식 문항·음원·제시 필드를 연결하고 교육 담당자와 채점 경계를 검수합니다. 비공개 파일 저장소에 업로드하고 검사 완료 파일만 접근 가능한 리소스 경로를 통해 제공합니다. 완료 기준은 재시작 뒤 동일 문항 재개, 동시 마지막 답안의 결과 중복 방지, 접근 권한 회수 직후 다운로드 차단입니다.
3. **팀 생성 기능과 비동기 작업 연결**
   실제 AI 사용이 필요한 경우 교사별 키를 서버에서 암호화하고, 선택 학생별 `ai_requests` 행에 입력·진단 스냅샷·모델·프롬프트 버전과 키를 고정합니다. 배치 요청은 교사·클래스·작업·부모 멱등키로 범위를 고정하고 정규화 본문을 비교합니다. 작업 결과가 불명확한 경우 `unknown`을 저장합니다. 완료 기준은 작업 중 재접속, 학생별 부분 실패 표현, 동일 요청의 중복 호출 방지, 생성 결과 검증 후 초안 저장입니다. 기존 DDL의 버전 비교에는 잠금 하에 `updated_at` 또는 별도 행 버전 방식을 확정합니다.
4. **정식 프론트엔드 화면과 운영 검증**
   초대·진단·업로드·검토·풀이 화면을 구현된 API에 연결합니다. 같은 출처의 HTTPS를 적용하고 계정 발급, 클래스 종료·권한 취소, 저장 기간·백업 복구 절차를 마련합니다. 두 역할로 교사 초대부터 배포·재풀이까지 확인하고 권한 경계, 느린 네트워크, 모바일·키보드 접근성을 검증합니다.

현 단계에서는 첨부 DDL·DML을 변경하거나 실행하지 않았습니다. 메모리 저장은 API·DTO와 업무 흐름 검증용이며, 장애 복구나 여러 서버 프로세스에서의 일관성은 MariaDB 연결 단계의 검증 항목입니다.
